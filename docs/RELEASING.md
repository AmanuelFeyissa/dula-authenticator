# Releasing

How a release is cut, what it contains, and how anyone can verify it — including
on a machine with no internet access.

## Cutting a release

1. Update the version in `pubspec.yaml` (`version: 1.2.3+4`). The release
   workflow **refuses to publish** if the tag and this field disagree, because
   artifacts whose filenames contradict their release are worse than a failed
   build.
2. Add the version's section to [`CHANGELOG.md`](../CHANGELOG.md).
3. Commit, then tag and push:

   ```bash
   git tag -a v1.2.3 -m "Dula Authenticator 1.2.3"
   git push origin main v1.2.3
   ```

`.github/workflows/release.yml` then builds every shipping target, packages
Linux, generates the SBOM, checksums and signs everything, and publishes the
GitHub Release. To exercise the pipeline without spending a version number, run
the workflow manually (`workflow_dispatch`): it builds and signs but skips
publishing.

## What a release contains

| File | What it is |
|---|---|
| `dula-authenticator-<v>-windows-x64.zip` | Windows build, unzip and run |
| `Dula_Authenticator-<v>-x86_64.AppImage` | Linux, single file, no install step |
| `dula-authenticator_<v>_amd64.deb` | Debian/Ubuntu package |
| `dula-authenticator-<v>-1.x86_64.rpm` | Fedora/RHEL-family package |
| `dula-authenticator-<v>-android.apk` | Android package |
| `dula-authenticator-<v>-web.tar.gz` | Static web build, serve it from anywhere |
| `dula-authenticator-<v>-sbom.cdx.json` | CycloneDX SBOM — every dependency, with a SHA-256 each |
| `SHA256SUMS` | Checksum of every file above |
| `SHA256SUMS.sig`, `SHA256SUMS.pem` | Sigstore signature and certificate for `SHA256SUMS` |

## Verifying a release

### Checksums

```bash
sha256sum -c SHA256SUMS
```

That proves the files are intact. It does not prove who made them — for that,
check the signature.

### Signature

Releases are signed with [Sigstore](https://www.sigstore.dev/) **keyless**
signing. There is no private key: the signature binds the artifacts to the
workflow that produced them, attested by a short-lived certificate issued
against GitHub's OIDC identity. Nothing secret exists to be stolen, lost or
rotated.

```bash
cosign verify-blob \
  --certificate SHA256SUMS.pem \
  --signature SHA256SUMS.sig \
  --certificate-identity-regexp '^https://github.com/AmanuelFeyissa/dula-authenticator/' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  SHA256SUMS
```

`--certificate-identity-regexp` is the part that matters. Without it, `cosign`
will happily verify a signature made by *anyone* with a valid Sigstore
identity; with it, you are asserting the signer was this repository's workflow.

### Verifying without internet access

The air-gapped case is one this project exists for, so it has to work
(ADR-0007).

`sha256sum -c SHA256SUMS` is entirely offline. Signature verification normally
reaches Sigstore's transparency log, which an air-gapped machine cannot do. Two
options:

- **Verify on a connected machine, then carry the artifacts across.** The
  checksum file is the link: verify the signature over `SHA256SUMS` where there
  is a network, then re-run `sha256sum -c SHA256SUMS` on the air-gapped side.
- **Verify offline with `--insecure-ignore-tlog`**, which checks the signature
  and certificate but not the log's inclusion proof:

  ```bash
  cosign verify-blob --insecure-ignore-tlog \
    --certificate SHA256SUMS.pem \
    --signature SHA256SUMS.sig \
    --certificate-identity-regexp '^https://github.com/AmanuelFeyissa/dula-authenticator/' \
    --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
    SHA256SUMS
  ```

  The flag is named the way it is for a reason: skipping the log means you
  cannot detect a signature that was later revoked or one that never appeared
  publicly. Prefer the first option where the choice exists.

## Reading the SBOM

`*-sbom.cdx.json` is [CycloneDX](https://cyclonedx.org/) 1.5. It lists every
Dart/Flutter package the build resolved, with the `pkg:pub/...` purl, the exact
version, and the SHA-256 that `pubspec.lock` recorded — so an auditor can
confirm each dependency independently rather than trusting the list.

Packages that only built the app (linters, test frameworks) are present but
marked `"scope": "excluded"`, so what ships is distinguishable from what was
merely needed to produce it.

```bash
# every dependency that actually ships
jq -r '.components[] | select(.scope=="required") | .purl' *-sbom.cdx.json
```

It is generated by `tool/generate_sbom.dart`, covered by
`test/tool/sbom_test.dart`, and honours `SOURCE_DATE_EPOCH` so the same commit
yields the same document.

## Supply chain

- Every GitHub Action is pinned to a **commit SHA**, not a tag. A tag can be
  moved to point at different code; a SHA cannot.
- The release is created with the preinstalled `gh` CLI rather than a
  third-party release action, which is one fewer dependency able to see the
  release token.
- The Flutter SDK version is pinned in both workflows, so a release builds
  against a known toolchain rather than whatever `stable` meant that day.

## Known gap: Android signing

`android/app/build.gradle.kts` still signs release builds with the **debug**
key, so the published APK is not suitable for Play Store distribution or for
establishing provenance by its signature. The checksums and the Sigstore
signature still establish that the APK came from this workflow. Proper signing
needs a keystore held as a repository secret, which is a decision for whoever
publishes rather than something to invent here.
